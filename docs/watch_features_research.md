# Ryze Wave — BLE Feature Planned-Work Report

Scope: synthesis of the per-feature reverse-engineering findings (decompiled Ryze Fit SDK + Gadgetbridge + our docs). **Nothing has been exchanged with the watch yet for these particular features** (the exercise/sync protocol in `docs/PROTOCOL.md` *is* hardware-verified), so every opcode layout below is a hypothesis from the SDK/GB until a logcat capture confirms it. "Risk" throughout means *brick/data-loss* risk unless stated; none of the feasible items touch the OTA/DFU UUIDs.

---

## Direct answers to your questions

**1. Can we push arbitrary contacts / call-log?**
- **Contacts: YES.** Opcode `37 FA`/`37 FB`/`37 FC` on the 34F1 data channel. The wire format only carries two byte-strings (number = ASCII ≤15, name = UTF-16BE, 10 or 20 chars per a feature bit), so we can push *any* name+number — the vendor's "numbers only from the address book" is a UI choice, not a protocol limit. Needs MTU negotiated up (~247) and an ack-driven pump. Effort M, low risk.
- **Call-log: NO over BLE.** There is no call-history/log opcode anywhere in the SDK, the opcode map, or any GloryFit reference, and the vendor app never reads CallLog despite holding the permission. The watch's "Call history" list is served over **classic-BT PBAP (SDP 0x112E)** automatically by Android once classic-paired — not reachable or spoofable from a BLE app. The only theoretical route (writing the phone's real CallLog provider so PBAP serves it) needs restricted `WRITE_CALL_LOG`, pollutes the real dialer, and is out of scope. What *is* feasible is **real-time incoming-call** push+control (see A6).

**2. Can we send music files to the watch to play later?**
- **NO.** There is zero mp3/wav/audio-file/upload opcode or UI in the SDK. Music is phone-playback remote-control + optional song-title display only. The only large-file transfer paths that exist are watch-face upload (26/27) and firmware OTA — neither carries audio. The watch can play *live* audio (calls, streamed music) purely as a classic-BT A2DP/HFP endpoint managed by Android; that is not a file store and we don't drive it. Standalone on-watch audio would need an undocumented Realtek storage protocol the vendor app never uses.

**3. Can we replace Bird Game with Snake?**
- **NO.** Games are baked into the monolithic Realtek firmware image; grep of the whole app finds zero game/app/bird/snake/flappy opcodes. There is no on-watch app/applet/resource abstraction on this RTL8762-class SoC. The only lever that touches the game is a full firmware OTA reflash — HIGH brick risk, vendor-keyed image, on the do-not-touch UUIDs. `F9` could at most *hide* a menu entry (if the game is one), never swap a game in. Not feasible short of a full closed-firmware RE project.

**4. Can we modify the watch face remotely?**
- **YES, with real effort (partly).** Custom photo-dial upload over `26`/`27` on the *normal* command characteristic (NOT the OTA UUIDs — this is a common misconception). We build the dial file on-phone (RGB565 big-endian, optional RLE, 24-byte element table, CRC-32 computed from offset 24, appended preview) from templates extracted from the APK's `DialCustom` assets — no vendor server needed. Effort L, **moderate** risk (`26 02` erases the on-watch dial slot; a bad file can leave a blank face, recoverable by re-upload). "Switch face without uploading" is *not* available on our (RK/classic) platform — there's no set-index opcode; only the JX/acts platform has apply-by-ID. Confirm platform from a scan first.

**5. Can we add app hooks for camera control and SOS?**
- **Camera: YES.** `C4 01` arm / `C4 03` disarm (phone→watch); watch emits `D1 11` open, `C4 02` shutter, `D1 0F` close. Effort M, low BLE risk — the real work is ordinary Android CameraX + launching an Activity from a background service.
- **SOS: PARTLY.** *Setting* the emergency contact = **YES** (`37 AC`/`37 AD FD`/`37 AE` on 34F1, effort S) — note firmware supports **one** SOS contact (vendor pushes only `list.get(0)`). *Handling the trigger* = **NO over BLE**: the watch dials the SOS number itself over its own classic-BT HFP link; there is no inbound SOS packet, so our app can't see or place the call. We provision, the watch dials.

**6. Can our app control which AI the voice assistant uses?**
- **Not over BLE, and mostly already solved at the OS level.** No audio/voice/mic opcode exists and the vendor app has no `RECORD_AUDIO` permission — the watch's voice button is a **classic-BT HFP** feature (`AT+BVRA` → SCO audio → Android's *default digital assistant*, which is why it lands on Gemini on the Pixel). The AI is therefore **already user-selectable**: Settings → Default apps → Digital assistant. To force it to Claude specifically we'd have to build/register an Android `VoiceInteractionService` (become the default assistant) and capture the SCO mic audio ourselves — feasible but effort L, system-wide, and **not a BLE feature**; our BLE client can never see the trigger.

## (A) Quick wins — feasible over BLE, low risk

Prerequisite for the whole group: read the watch's **feature bitmap** (`characterisicFunctionList5`/`6`) once at connect — it gates alarm mechanism, name length, weather/extended forms, music bits, and which settings toggles the watch actually has. We have never read it.

**A1. Alarms** — `AB <cycle> HH mm …` (classic, single write) or `51 <seq>…/51 FD <xor-crc>` (labeled, chunked, UTF-16BE label) on 33F1/34F1. Feasibility YES. Effort S (classic) / M (labeled). Risk low.
- Probe `51 AA`; if the watch answers `51…` use the labeled path, else classic `AB`.
- Add `enc_alarm_classic(id,on,hh,mm,cycle,shake)` with cycle helpers (62=weekdays, 127=daily, days→bitmask bit0=Sun..bit6=Sat — confirm on watch).
- Add `enc_labeled_alarms()` (15+label-byte records, chunk = maxCommLen-2, running XOR CRC, `51 FC` empty, `51 AA` query).
- Test: push one alarm, eyeball on watch, toggle off.

**A2. Reminders + DND + goals + period + units/clock** — fixed short writes on 33F1: sedentary `D3`, drink-water `D4`, wash-hands `41` (identical 12-byte layout); DND `D7 <flags> <fromH><fromM><toH><toM> <sw>`; goals `3F 01` standing (value=hrs×60) / `3F 02` exercise; period `29 <en> <yr16><mon><day><days><cycle>`; units+clock `A0 <km1/mi2> <24h1/12h2>`. Feasibility YES. Effort S each. Risk low.
- Port each as a static-packet encoder into `ryzewave/protocol.py`.
- Correct the docs: A0 is **3 bytes** `A0 <unit> <fmt>` (docs currently guess a 2-byte form).
- Gate each toggle on its feature bit before exposing it in the UI.

**A3. Find watch / find phone** — `AB 00 00 00 01 <n> 07 01` (find watch, already stubbed in protocol.py); `D1 0A <0/1>` find-phone enable, watch initiates the ring and we must ring the phone on the inbound `D1 0A` notify. Feasibility YES / partly (find-phone). Effort S. Risk low.
- Wire find-watch through the bridge; add an inbound `D1 0A` handler that rings the phone.

**A4. Weather push** — `CA …` (today+tomorrow, 14 B) and `CB 01/02/03` (7-day; `CB 01` 19 B or 21 B when feature-6 bit 0x800 adds humidity+UV), plus `CB FF` English city name. Feasibility YES. Effort M (needs an external data source). Risk low.
- Port `weatherConditionCode()` (QWeather codes → 1..12) and `getAbsolute()` (negative temp = abs|0x80).
- Pick a vendor-independent source (Open-Meteo) + geocode; map its condition codes into the 1..12 buckets.
- Implement CA then the three CB sections; ASCII/skip city name for non-zh.

**A5. Contacts push** — `37 FA <count>` → N `37 FB` section frames → `37 FC FD` on 34F1; number ASCII (spaces stripped, ≤15), name UTF-16BE (≤10, or ≤20 when feature-6 bit 0x80000 set). Feasibility YES. Effort M. Risk low (but `37 FA` appears to **replace** the whole list, not append — inference).
- Add `enc_contacts()` building the FA/FB/FC frames, packing whole entries per MTU-sized frame.
- Negotiate MTU up first; fall back to 1 contact/packet at the 23-byte default.
- Implement the ack-driven pump (send FA, wait notify, one section per `37 FB` ack, FC FD).
- Add a Contacts screen (read Android contacts or manual entry). Reuses the same ack pattern as labeled alarms (A1).

**A6. Incoming-call notify + control** — outbound: name `C5 <idx>…/C5 FD` (payload `[type=00][len][UTF-16BE]`), number `45 FA <len><digits>`, vibrate `AB 00 00 00 01 0A 02 01`, dismiss `C1 04`; inbound: `D1 02` reject/hangup → `TelecomManager.endCall()`, `D1 12 ..02` mute ringer, `52 …` SMS quick-reply (ack `52 FE`). Feasibility YES (this is the achievable half of the "call" ask). Effort M. Risk low. (No "answer call" opcode exists — answering is HFP audio over classic BT.)
- Add a `PhoneStateListener`/`TelephonyCallback`; on RINGING push C5 name + `45 FA` number + AB vibrate.
- On OFFHOOK/IDLE send `C1 04`; stop vibration with the AB-zero form.
- Parse inbound `D1 02`/`D1 12`/`52` and act (endCall / mute / send SMS + `52 FE`).

**A7. Camera remote shutter** — arm `C4 01` / disarm `C4 03` (phone→watch); inbound `D1 11` open, `C4 02` shutter, `D1 0F` close (Gadgetbridge variant uses `C4 01/02/03` — handle both). Feasibility YES. Effort M. Risk low (BLE); real work is Android camera.
- Extend the parser: `D1 11`→CameraOpen, `D1 0F`→CameraClose, keep `C4 02`→CameraShutter (currently parsed but dropped at `else -> Unit`).
- Add a `CameraController` (mirror `FindPhoneRinger`): on open arm+launch, on shutter `ImageCapture.takePicture()`, on close disarm+finish.
- Add a CameraX Activity + `CAMERA` permission + a full-screen-notification launch path from the background service.

**A8. SOS contact set** — `37 AC <count>` + inner `37 AC <numLen><nameLen><num><name>` padded to ~244 B, commit `37 AD FD <crc>`, clear `37 AE`; one contact only. Feasibility YES (setting) / NO (trigger). Effort S. Risk low.
- Add `sos_set(name,number)` / `sos_clear()`; number ASCII ≤15, name UTF-16BE (try 20, fall back to 10).
- Clear-before-set for safety (as GB does); watch `37 AD` ack = success.
- Do **not** try to handle the trigger — no BLE path; watch dials over HFP, needs no CALL_PHONE permission from us.

**A9. World clock** — `43 FA <count> …` entries + `43 FD <xor-crc>`, delete `43 FB`, on 34F1. Feasibility YES. Effort S/M. Risk low. Add an encoder (region name UTF-8 + tz offset) and drive via the bridge.

## (B) Bigger builds — feasible but medium/large

**B1. Device-settings screen** — bundles the A2 toggles plus wrist/wear detection `3D 01/00`, screen orientation `DF 01/02` (gated feature bit 32), off-screen time + raise-to-wake (both inside the 19-byte `A9` user-info packet), show/hide watch pages `F9` + query `F9 AA`, language `AF AB <n>`. Feasibility YES. Effort M. Risk low **except A9**.
- Build the fixed-packet encoders (`3D`, `DF`, `F9`, `AF AB`).
- **A9 hazard:** it is one packet carrying the whole user profile + several settings — always rebuild the *complete* current profile when changing any one field, or you clobber height/weight/goal/HR-alarms/units. Fix the existing `enc_user_info` (byte5=off-screen time, byte10=raise-to-wake, byte16=language, byte17=temp unit — currently mislabeled/hardcoded).
- Capture `F9 AA` on hardware to learn this watch's page-id list before offering show/hide (0xFF hides everything).
- Gate every toggle on the feature bitmap, exactly as the vendor does.
- **Drop themes / always-on-display / brightness** — no opcode exists for any of them (see D).

**B2. Watch-face upload (custom photo dial)** — `26 01` query config, `26 02` prepare/erase, `27 <idxHi><idxLo> <payload=MTU-3>` sections with `26 03 04` per-4 KB-block flow control and `26 03 03` resume, `26 03 00` finish. On the normal command char, **NOT** the OTA UUIDs. Feasibility partly/YES. Effort L. Risk **moderate** (erases the dial slot; bad file = blank screen, recoverable). See also C — this is what people mistakenly lump with OTA.
- Confirm platform first (adv "55 55" or name "AT" ⇒ JX; else RK/classic — expected). This decides 26/27 vs the `01 E3` acts path.
- Capture the vendor doing one upload via logcat to get the exact `26 01` config bytes + a full `27` stream as ground truth.
- Extract the `DialCustom/dial_*_{240x240|320x360}` templates from the APK; port the encoder (RGB565 BE, optional RLE with the `30 10 w h 01 1B` head when compatibleLevel≥2, 24-byte element table, `fileSize@4`, `CRC-32-from-offset-24@8` little-endian, appended preview). **Unit-test the CRC/byte layout against a captured good .bin before any radio use.**
- Gated hardware test with a known-good captured image; keep a good face ready to re-upload.
- Note: pure "switch active face" is unavailable on RK (no set-index opcode).

**B3. Music control (+ optional title display)** — inbound `D1 07/08/09/0D/0E` (play-pause/next/prev/vol±) on 33F2 → `AudioManager.dispatchMediaKeyEvent`/`adjustStreamVolume`; optional phone→watch title `3A 01/06/FA` + `D1 0C` state + `D1 0D/0E` vol%, gated by feature-5 bits 1/4096. Feasibility YES (control) / NO (file storage). Effort M. Risk low.
- Subscribe to 33F2, decode the D1 sub-codes into a MusicEvent enum.
- Dispatch media keys (126/127/87/88) to the phone's active session (needs no session ownership).
- For true play/pause state + title push, add a `NotificationListenerService` + `MediaSessionManager` (needs notification-listener grant).
- Confirm the watch's music feature bits on hardware first.

**B4. Voice-AI routing to Claude** — no BLE opcode; classic-BT HFP `AT+BVRA` → SCO audio → Android default assistant. Feasibility partly. Effort L. Risk low (no watch writes at all).
- First *confirm* the mechanism without touching the watch: pair the watch as an HFP headset, press the voice button, logcat for `BVRA`/`startVoiceRecognition`/SCO state and which package launches.
- Verify the target is configurable by changing Settings → Default digital assistant and re-pressing.
- **Simplest path:** just set the phone's default assistant to a preferred app (or a thin forwarder to Claude) — zero protocol work.
- **Full path (if we must own it):** build a `VoiceInteractionService`, take `RECORD_AUDIO`/`MODIFY_AUDIO_SETTINGS`, register as default assist, capture the SCO mic → SpeechRecognizer → Claude API. System-wide, not a BLE feature.

## (C) Risky / needs care — explicit go-ahead only

**C1. Firmware OTA/DFU** — Realtek `0000d0ff-…` / silent-mode `00006287-…` / Dialog SUOTA `0000fef5` (+ patch `0000ffd3`). **HIGH brick risk**, vendor-keyed image, no SWD/UART recovery noted. Never write from our app; leave firmware updates to the vendor app. This is the *only* path that could touch the game (B... rather D3).

**C2. Factory reset `AD`** — bare single byte, wipes ALL watch data — trivially fired by accident. Keep it behind an explicit confirm as protocol.py already does; never send in normal flows. Note `AlarmUtil` can trigger it indirectly via an "all alarms deleted" push — guard that path.

**C3. Set password `D5 03 <ascii>`** — could lock us out of our own watch. Do not drive.

**C4. Sensor calibration** — `24 07` (temp), `FB` (HR), `FC` (turn-wrist), `AF 00` — can miscalibrate readings. Avoid unless deliberately recalibrating.

**C5. Dial upload (26/27)** — *listed here for completeness because it's often lumped with OTA, but it is NOT on the OTA UUIDs* and is recoverable (see B2). Moderate, not high, risk. The genuine care item is that `26 02` erases the slot.

**Activation-gated (blocked, not dangerous):** EL-BP `55`, cSBp `3E`, mood/stress/fatigue `44` all need a per-device vendor activation code we don't have (`44 0E`/`setBpActivationCode` fetch it from a vendor server). Can't drive without it.

## (D) Not feasible / firmware-only

**D1. Replace Bird Game with Snake — NO.** Games are baked into the monolithic Realtek firmware; no game/app opcode exists and this SoC family has no on-watch app abstraction. Only firmware OTA could touch it (C1, HIGH risk, vendor-keyed). `F9` can at most hide a menu entry. Recommend not pursuing without a dedicated firmware-RE track.

**D2. Music file upload / standalone playback — NO.** No audio-file opcode or UI anywhere; music is control + metadata only (see #2 / B3).

**D3. Call-log / history push — NO over BLE.** No opcode; the list is classic-BT PBAP served by Android (see #1). Only the real-time incoming-call surface (A6) is feasible.

**D4. Themes / Always-On Display / screen brightness — NO.** Grep finds no AOD/ambient, no brightness, and no discrete theme/dial-select opcode. A watch's *look* changes only by uploading a whole dial (B2). Drop these three from any settings screen.

**D5. Marketing sensors — skip.** Blood sugar `5B` (optical wrist glucose = pseudoscience), body composition `E9`, legacy BP `C7/C8` (not medical), ECG `28` (watch likely lacks electrodes; HRV exists only as an ECG-derived field, no standalone opcode). Also skip account-ID `33` (feature bit off), Alipay/WeChat-Pay (China-only).

## Recommended order of work

1. **Read the feature bitmap** (`functionList5`/`6`) at connect — unblocks alarm mechanism, contact name length, weather/settings extended forms, music bits. Do this first; it decides several branches below.
2. **A2 fixed-packet quick wins** — units/clock `A0`, DND `D7`, reminders `D3/D4/41`, goals `3F 01/02`, period `29`, find-watch. Highest value-per-effort, all S, all safe. Correct the `A0` and `A9` field maps in docs while here.
3. **A1 alarms** — probe `51 AA`, ship classic `AB`, then labeled `51` (introduces the chunk+XOR+ack pattern reused later).
4. **A4 weather** — needs a data source; on-brand since we're vendor-independent.
5. **A5 contacts** + **A8 SOS-set** — contacts brings the MTU/ack pump; SOS-set reuses the same encoder.
6. **A6 incoming-call** + **B3 music control** — the two notification/media features; both need the notify-subscribe + Android glue.
7. **A7 camera** — trivial BLE, mostly CameraX plumbing.
8. **B1 device-settings screen** — bundle 2, 5-part items into one UI; handle the `A9` full-profile hazard carefully.
9. **B2 watch faces** — the big one; do the capture + offline-CRC-validation before any gated hardware test.
10. **B4 voice-AI routing** — optional, separate Android-assistant track; start with the "just set the default assistant" shortcut.
11. **Never:** OTA/DFU (C1), factory reset (C2), password (C3), calibration (C4), and firmware reflash for games (D1).

Honest caveats: all opcode layouts are SDK/Gadgetbridge inference — capture and verify each on our watch (Ryze Fit logs every BLE packet to logcat) and mark `docs/PROTOCOL.md` entries verified as you go. The `51`-vs-`AB` alarm choice, contact replace-vs-append semantics, the RK-vs-JX platform, day-bit ordering, and the dial CRC are the specific unknowns to confirm before shipping each feature.

### Voice assistant (watch mic button -> phone digital assistant / "Gemini")

- **Feasible:** partly  **Effort:** L
  **Opcodes:** `(none - no audio opcode exists in the SDK)`, `D1 11 (contrast: remote-camera trigger CAMERA_ATIVITY)`, `D1 0A (contrast: find-phone)`, `D1 07/08/09 (contrast: music control)`, `AT+BVRA=1 (classic-BT HFP AT command, inference - not a BLE opcode)`

- **What it does:** Pressing the watch's voice-assistant button/gesture wakes the phone's default digital assistant (Gemini/Google Assistant on the Pixel) and uses the WATCH's built-in microphone as the audio input, so the user speaks into the watch and the phone's assistant answers. This is a firmware + Android-OS feature; it is NOT implemented in, and does not pass through, the Ryze Fit companion app at all.
- **Mechanism:** No BLE mechanism exists in the vendor SDK for this. Evidence: (1) captures/sdk_opcode_map.txt (158 lines) has ZERO audio/voice/mic/record opcodes; the D1 command handler in BluetoothLeService.datePacketOperate (~L3027) decodes only music (D1 07/08/09), volume (D1 0D/0E), find-phone (D1 0A) and remote-camera (D1 11 -> ICallbackStatus.CAMERA_ATIVITY) - there is no sub-code that launches an assistant. (2) The decoded AndroidManifest (from apk/xapk/com.yc.ryzefit.apk) declares NO android.permission.RECORD_AUDIO / CAPTURE_AUDIO_OUTPUT, NO VoiceInteractionService, and NO VOICE_COMMAND / VOICE_SEARCH / ASSIST / RecognizerIntent (all grep counts = 0). So the vendor app literally cannot record or route audio. (3) The only "voice"/"audio" code (VoiceUtil.java, AudioManagerUtil.java, BluetoothLeService HEAD_SET_VOICE_ACTION @L6837) is text-to-speech playback of sport stats (num_*.raw), not recording. INFERENCE (strongly supported): the watch is a dual-mode device exposing classic-BT Hands-Free Profile (HFP 0x111E, verified via SDP in docs/PROTOCOL.md L9). The voice button is a standard HFP feature - the watch sends the AT command AT+BVRA=1 (Bluetooth Voice Recognition Activation) over the classic RFCOMM/HFP channel; Android's HFP/Headset stack answers by opening a SCO audio link and launching the phone's configured default assistant via the framework voice-recognition path. Watch mic audio streams to the phone over the classic-BT SCO channel, NOT over BLE and NOT through Ryze Fit. "Gemini" is just the Pixel's default digital assistant, so the generic Android trigger lands there.
- **Risk:** LOW for bricking - this feature touches nothing on the OTA/DFU (0000d0ff/00006287) or dial-upload (26/27) UUIDs and requires NO writes to the watch firmware. It is entirely classic-BT HFP/SCO plus the Android assistant framework. The only caveats are intrusiveness (to intercept the trigger our app must become the phone's system-wide default digital assistant) and the fiddliness of capturing HFP/SCO mic audio. There is no BLE write to the watch involved for this feature at all, so no watch-side risk.

### SOS emergency contact (set contact via app; watch-triggered SOS call)

- **Feasible:** partly  **Effort:** S
  **Opcodes:** `37 AC`, `37 AD`, `37 AE`, `37 AD FD`

- **What it does:** The user stores an SOS/emergency contact (name + phone number) in the vendor app, which pushes it to the watch. When SOS is triggered ON the watch (a watch-side button/menu action — there is no app involvement in triggering), the watch itself places a phone call to the stored SOS number over its own classic-BT HFP audio link to the paired phone. Key finding: although the vendor UI (SosCallActivity, MAX_COUNT=5) lets the user save up to 5 contacts, WriteCommandToBLE.syncSosCallContacts only ever pushes list.get(0) — the watch firmware effectively supports ONE SOS contact. The BLE side is purely a provisioning channel: the app never receives an SOS-trigger packet and never places a call or SMS itself for SOS.
- **Mechanism:** Characteristic 000034f1 (service 000056ff) — the shared "data" channel, via writeCharaBle5; NOT any OTA/DFU or dial-upload UUID. Opcode 37 (contacts) with SOS sub-commands. Set: outer header `37 AC <count>` then per-contact inner block `37 AC <numLen> <nameLen> <numberBytes> <nameBytes>`, whole packet zero-padded to the negotiated max length (Gadgetbridge pads to 244). numberBytes = ASCII digits, spaces stripped, max 15 (int2unicode of digit chars collapses to plain ASCII; GB uses number.toByteArray()). nameBytes = UTF-16BE (string2unicode), name truncated to 20 chars if feature bit Sixth(0x80000=524288) is set else 10; nameLen is the byte length (2×chars). Commit/end: `37 AD FD <crc>`, crc = XOR of the AC packet bytes from index 2 onward (GB hardcodes 0xC1, hinting the watch may not strictly validate the CRC — inference). Clear all: `37 AE` (only sent when the list is empty). Watch acks are parsed in BluetoothLeService.dealWithContacts (~L7660): sub 0xAC = section received (app sends next/end), 0xAD = end OK -> status 214 SYNC_SOS_CALL_COMMAND_OK, 0xAE = cleared. No incoming opcode exists for an SOS trigger.
- **Risk:** Low. All SOS writes land on the 000034f1 "data" characteristic (contacts subsystem) — NOT the Realtek/Dialog OTA/DFU UUIDs (0000d0ff/00006287/0000fef5) and NOT the watch-face dial-upload path, so no firmware/brick risk. Worst realistic failure from a malformed 37 AC/AD packet is a rejected or garbled contacts entry, not a brick; 37 AE clears it. Our app places NO calls and NO SMS for SOS — the watch dials the SOS number itself over its independent classic-BT HFP link, so we need no CALL_PHONE / SEND_SMS permission and there is no risk of us auto-dialing. (The vendor's CALL_PHONE/TelecomManager/SmsManager usage is for the separate incoming-call-reminder and reject-with-SMS features, not SOS.)

### Watch faces (online-dial / custom watch-face upload + switch)

- **Feasible:** partly  **Effort:** L
  **Opcodes:** `26 01 (query dial config)`, `26 02 (prepare/erase)`, `27 <idxHi> <idxLo> <payload> (data section, payload=MTU-3)`, `26 03 00 (finish / success ack)`, `26 03 04 (per-erase-block flow-control ack)`, `26 03 03 <idxHi> <idxLo> (resume from section)`, `26 03 01 / 26 03 02 (fail)`, `01 E3 AA 0B (acts getWatchFaceInfo, JX only)`, `01 E3 AB 05 <id> <ver> <op> (acts applyWatchFace/switch, JX only)`, `01 E3 AB 03/04 01 <type> (acts prepare/finish)`, `01 E3 <lenHi> <lenLo> FD <xorcrc> (acts data finish)`, `01 E4 AA 02 01 <n> (acts image-watchface download)`

- **What it does:** The watch stores multiple watch faces ("dials") in an internal flash region. The vendor Ryze Fit app offers three things: (1) query the watch's dial capability (screen resolution, shape/screen-type, max dial-file size, "compatible level", corner radius); (2) upload a dial binary into the slot - either a pre-made design downloaded from the vendor server, or a CUSTOM photo dial built on the phone from a user-chosen background image + font color; (3) on some hardware, switch/apply a face by ID and configure an "image watch face" with widgets. All of this is watch-face content only - it is a completely separate flow from firmware OTA/DFU.
- **Mechanism:** Two code paths, BOTH over the ordinary command characteristics (write 000033f1 / BLE5 write 000034f1, notify 33f2/34f2) - they NEVER touch the OTA UUIDs (d0ff/6287/SPOTA). CLASSIC path (RK/Realtek platform = almost certainly ours): opcode 26/27. `26 01` queries config; response bytes: [2..5]=dialNumber BE32, [6..7]=width, [8..9]=height, [10]=screenType, [11..14]=maxDataSize BE32, [15]=compatibleLevel, [17]=cornerAngle (OnlineDialUtil.getDial* L97-134). `26 02` = prepare (triggers an on-watch flash erase, then it replies ready). `27 <idxHi> <idxLo> <payload>` streams sections, payload = (negotiated MTU - 3) bytes (WriteCommandToBLE.sendSectionOnlineDialData L2130). Flow control: at every 4096-byte erase boundary the phone waits for notify `26 03 04` before continuing; `26 03 03 <idxHi><idxLo>` = resume-from-section. `26 03 00` = finish; watch replies `26 03 00` success / `26 03 01`/`02` fail / a CRC-fail path (dealWithOnlineDial, BluetoothLeService L6153). ACTS path (JX/Actions ATS3085 platform, probably NOT ours): headers `01 E3`/`01 E4`, running XOR-8 checksum, subcommands AA/AB/FD incl. `01 E3 AB 05 <id> <ver> <op>` applyWatchFace (switch by ID) and `01 E3 AA 0B` getWatchFaceInfo (ActsDialCommandUtil). DIAL FILE FORMAT (custom photo dial, built fully on-phone by Rgb.java/PicUtils.java, no server): pixels are RGB565 stored big-endian per pixel (Rgb.RGB888ToRGB565 L44, byte order L191-201); optional row-RLE compression when compatibleLevel>=2, preceded by 8-byte head `30 10 <wHi><wLo> <hHi><hLo> 01 1B` (addHeadBeForeCompress); the file is a container = a table of 24-byte element records (type BE16 at off0, width, height, picStartAddress LE32, ...) that the app assembles from the APK asset folder assets/DialCustom/dial_*_{240x240|320x360}/ (per-element PNG layers + config txts naming placement `<w>x<h>_<x>x<y>`); integrity = CRC-32 (reflected/zlib standard table) computed over bytes from OFFSET 24 to end (Rgb.uteDataCrc32) stored little-endian at file offset 8, with total fileSize at offset 4; a RGB565 preview thumbnail is appended (compositePreviewToByte). Platform (JX=1 vs RK=2) is chosen at scan time: adv contains "55 55" or name starts with "AT" => JX else RK (ScanConnectProcess L194-215, DevicePlatform).
